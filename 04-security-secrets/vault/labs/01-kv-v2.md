# Lab 01 : KV v2, le coffre de secrets statiques

**Objectif :** stocker et versionner des secrets, et comprendre que le CLI n'est qu'une surcouche de l'API HTTP.

```bash
source labs/env.sh
```

## 1. Découvrir ce qui est monté

```bash
vault secrets list -detailed
```

En mode dev, `secret/` est déjà monté (KV v2). On va monter notre propre engine pour bien voir le mécanisme :

```bash
vault secrets enable -path=lab -description="mon lab" kv-v2
vault secrets list
```

> 💡 Un secrets engine se monte sur un **chemin**. On peut monter plusieurs KV (`team-a/`, `team-b/`) : c'est une façon courante d'isoler des équipes.

## 2. Écrire, lire, versionner

```bash
vault kv put lab/app/config user=admin password=s3cr3t
vault kv get lab/app/config
vault kv get -field=password lab/app/config     # une seule valeur, pratique dans un script
vault kv get -format=json lab/app/config        # sortie JSON

# Nouvelle version
vault kv put lab/app/config user=admin password=v2
vault kv get -version=1 lab/app/config          # l'ancienne version est toujours là

# Modifier UNE clé sans écraser les autres
vault kv patch lab/app/config password=v3
vault kv get lab/app/config                     # user est toujours là, version 3
```

⚠️ Piège classique : `kv put` **remplace** tout le secret. `vault kv put lab/app/config password=x` supprime `user`. Pour modifier une seule clé, utilise `kv patch`.

## 3. Le cycle de vie : delete, undelete, destroy

```bash
vault kv delete lab/app/config                  # soft delete de la dernière version
vault kv get lab/app/config                     # erreur : la version est marquée supprimée
vault kv undelete -versions=3 lab/app/config    # récupérée !

vault kv destroy -versions=1 lab/app/config     # suppression DÉFINITIVE de la v1
vault kv metadata get lab/app/config            # observe destroyed=true sur la v1

vault kv metadata delete lab/app/config         # supprime tout : versions et métadonnées
```

Limiter le nombre de versions conservées :

```bash
vault kv put lab/app/config a=1
vault kv metadata put -max-versions=3 -custom-metadata=owner=youssef lab/app/config
for i in 2 3 4 5; do vault kv put lab/app/config a=$i >/dev/null; done
vault kv metadata get lab/app/config            # seules les 3 dernières versions restent
```

## 4. Check-and-set (éviter d'écraser la modif d'un collègue)

```bash
vault kv put -cas=0 lab/app/new k=v             # cas=0 : n'écrit que si le secret n'existe pas
vault kv put -cas=0 lab/app/new k=v2            # erreur : il existe déjà
vault kv put -cas=1 lab/app/new k=v2            # OK : on part bien de la version 1
```

## 5. Le même travail via l'API HTTP

C'est ce que font les applications. Note bien le **`/data/`** dans l'URL :

```bash
# Écriture
curl -s -H "X-Vault-Token: root" -X POST \
  -d '{"data":{"user":"api","password":"fromcurl"}}' \
  $VAULT_ADDR/v1/lab/data/app/api | jq

# Lecture
curl -s -H "X-Vault-Token: root" $VAULT_ADDR/v1/lab/data/app/api | jq .data.data

# Lister les clés : passe par /metadata/
curl -s -H "X-Vault-Token: root" -X LIST $VAULT_ADDR/v1/lab/metadata/app | jq .data.keys
```

Astuce : `vault kv get -output-curl-string lab/app/api` affiche la commande curl équivalente à n'importe quelle commande CLI.

> 🧠 **À retenir :** en KV v2, les données sont sous `<mount>/data/<chemin>` et les versions/métadonnées sous `<mount>/metadata/<chemin>`. Le CLI `vault kv` ajoute ces préfixes pour toi, **mais pas les policies** (lab 02). C'est l'erreur n°1 des débutants.

## 6. Lien avec ton tuto ESO

Ton `ClusterSecretStore` utilise `path: kv/org` et `version: v2`, et l'ExternalSecret `dev` demande `version: "2"`. Va voir dans l'UI la correspondance entre `kv/org/dev` et ses versions, puis teste :

```bash
vault kv put kv/org/dev api-key=dev-key-v3
# Le secret k8s change-t-il ? Non : l'ExternalSecret dev est épinglé sur la version 2.
kubectl -n demo get secret dev-api-credentials -o jsonpath='{.data.api-key}' | base64 -d; echo
```
