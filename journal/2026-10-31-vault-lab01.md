# 2026-10-31 : Vault, lab 01 (KV v2)

## Ce que j'ai appris

- Dans Vault, **tout est un chemin**. Un secrets engine est un plugin monté sur un chemin (`vault secrets enable -path=lab kv-v2`).
- `vault status` : `Storage Type inmem` = mode dev, et tout est perdu au redémarrage (c'est ce qui avait cassé mon tuto ESO).
- En KV v2, `lab/app/config` correspond en réalité à `lab/data/app/config` (valeurs) et `lab/metadata/app/config` (versions, list). Le CLI ajoute ces préfixes, **pas les policies**.
- `kv put` **remplace** tout le secret, `kv patch` fusionne. **Toute** écriture crée une version, même si la valeur est identique.
- Trois niveaux de suppression : `delete` (soft, réversible avec `undelete`), `destroy` (définitif, ne remplit pas `deletion_time` mais met `destroyed=true`), `metadata delete` (tout).
- Détruire un secret qui a fuité ne suffit pas : il faut **révoquer ou changer le mot de passe à la source**.
- API : la réponse est `.data.data` (enveloppe Vault, puis données KV v2). On liste via `/metadata/` avec la méthode HTTP `LIST`.
- Mauvais token → **403** générique. Vault ne dit jamais si un secret existe, pour empêcher l'énumération.
- `max-versions` limite l'historique. `-cas=N` (verrouillage optimiste) évite d'écraser la modif d'un collègue, et `-cas=0` crée seulement si le secret n'existe pas.

## Erreurs rencontrées

- `curl` sans sortie : `$VAULT_ADDR` vide dans un nouveau terminal → `source labs/env.sh`.
- `kv metadata get -field` n'existe pas → `-format=json | jq`.
