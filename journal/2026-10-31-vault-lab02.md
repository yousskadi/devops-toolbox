# 2026-10-31 : Vault, lab 02 (policies et tokens)

## Ce que j'ai appris

- Vault **refuse tout par défaut**. Une policy est une liste blanche *chemin → capabilities*.
- Les capabilities sont des opérations API : `read` (et non « get »), `create`, `update`, `patch`, `delete`, `list`, `sudo`, `deny`.
- Sur `/metadata/`, `list` (voir les noms) et `read` (voir l'historique) sont **deux droits différents**. C'est ce qui m'a piégé sur `kv metadata get`.
- `vault token capabilities <token> <chemin>` est l'outil de debug n°1.
- La policy `default` est ajoutée à tous les tokens (lookup-self, renew-self, cubbyhole).
- Une policy modifiée s'applique **immédiatement** aux tokens existants, qui ne portent que le nom de la policy.
- Avec plusieurs policies, le chemin le plus spécifique gagne, et **`deny` l'emporte toujours**.
- `ttl` est une minuterie, `explicit-max-ttl` un mur absolu depuis la création. Un `renew` ne dépasse jamais le mur, et l'appli doit alors se ré-authentifier.
- Révoquer un parent révoque ses enfants en cascade. Un enfant ne peut pas avoir plus de policies que son parent (anti-élévation de privilèges).
- **Accessor** : il permet de gérer un token (lookup, revoke) sans pouvoir l'utiliser, comme le numéro de dossier d'une carte bancaire.
- **Response wrapping** : un ticket de consigne à usage unique, avec TTL, qui ne contient pas le secret. Un ticket déjà consommé avant le destinataire signale une **interception**.

## Erreurs rencontrées

- `"get"` n'est pas une capability → `read`.
